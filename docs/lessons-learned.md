# 经验教训（Lessons Learned）

## 2026-07-06：RAG 强制检索实现

### 1. LLM 不保证 100% 遵循 system prompt

**现象**：即使 system prompt 写了"必须先用 search_docs 检索"，模型在开放式问题上仍可能直接自答。

**原因**：工具调用是概率行为，受温度、模型版本、问题表述、工具描述强弱影响。

**做法**：对关键路径必须加代码层兜底，不能纯依赖 prompt 工程。

---

### 2. 强制调用工具时必须保持对话历史合法

**现象**：如果直接插入一条 `role: "tool"` 消息而没有前置 assistant `tool_calls`，OpenAI 兼容 API 会行为异常。

**做法**：`_force_tool_call()` 中伪造一条完整的 assistant tool_call，再插入 tool 结果，确保 `tool_call_id` 对应。

---

### 3. 测试环境编码问题会误导排查

**现象**：Git Bash 下 curl/Python 发送中文表单到本地 Docker，后端收到乱码，一度怀疑是代码编码问题。

**原因**：Git Bash / Windows 终端字符集环境导致，不是后端 bug。

**做法**：验证 UTF-8 行为时优先用浏览器或生产环境；本地 curl 测试用英文 query 避免干扰。

---

### 4. docker cp + restart 是快速验证，但不是最终交付

**现象**：本次用 `docker cp` 把新代码塞进运行中容器验证，速度快。

**风险**：容器 recreate 后改动丢失，且镜像没更新。

**做法**：验证通过后必须提交源码并重建镜像（`docker compose up -d --build`），才能把改动正式烤进去。生产部署必须走 build 流程。

---

### 5. 小改动也要同步文档

**现象**： initially 只更新了 dev-log 和 PROJECT-STATE，没写学习文档，用户指出遗漏。

**做法**：代码改动 + 项目文档 + 学习文档三位一体。学习文档要写得足够基础、详细，能作为后续复习和面试讲解材料。

---

### 6. 控制粒度要适度

**现象**：只在 `turn == 0` 强制检索，而不是每轮都强制。

**原因**：过度控制会让 Agent 失去灵活性；首轮保证检索即可，后续交给模型自主决定是否需要进一步工具链。

**做法**：设计兜底机制时，明确兜底范围（when/which turn/which tool），避免一刀切。
